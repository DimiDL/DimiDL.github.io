Bug 2064781 · Toolkit :: Form Autofill · ML mechanism

Address autofill fails on Firefox 154 because the shipped int8 classifier overflows ONNX Runtime's AVX2 accumulator

Firefox 154 enabled ML address-field detection for all desktop channels and switched the classifier to an int8-quantized build. That build uses per-channel weight quantization, which is the recommended practice but is unsafe on x86-64 CPUs with AVX2 and without VNNI. On those machines the int16 accumulation inside ONNX Runtime's u8s8 kernel saturates, the model collapses onto a single dominant label, and no address section is ever formed.

1. What changed in Firefox 154

Bug 2052140 (e1a3d03, landed 2026-07-03, first shipped in 154) made three changes to FormAutofillML.sys.mjs at once:

The live Remote Settings record for formfill-classification in main/ml-inference-options sets dtype: "q8" explicitly, on mozilla/tinybert-address-autofill revision v0.2.0. This was a deliberate configuration, not a missing field.

Important constraint on any fix

v0.2.0 ships only onnx/model_quantized.onnx on model-hub. onnx/model.onnx returns 404. Pinning dtype: "fp32" — either in-tree or by editing the Remote Settings record — would fail engine creation outright rather than fix anything.

2. Observed symptom

Both reporters run 154.0, buildID 20260812182057, Windows x86-64, with useml.successful = true and useml.nativeOnnxAvailable = true. The autofill devtools panel shows reason: ml on every address field, so inference ran and returned; it did not time out or throw. Every label it produced was either other or address-level2 — including on a phone field and a password field.

A model that is merely inaccurate spreads its errors around. This one had collapsed onto a single class, which is the signature of input that is off the distribution the classifier was fitted on.

4. The mechanism

4.1 How ONNX Runtime multiplies on pre-VNNI x86

Both revisions are quantized u8s8: uint8 activations times int8 weights, through 26 MatMulInteger nodes, weights spanning the full int8 range and no reduce_range applied. On x86-64 with AVX2 but without VNNI, ONNX Runtime's MLAS kernel has no dot-product instruction available, so it uses VPMADDUBSW, which multiplies two adjacent operand pairs and sums them into int16 before VPMADDWD widens to int32. 

a[k]   * b[k]        max 255 x 127 =  32,385     // one product nearly fills int16
a[k+1] * b[k+1]      max 255 x 127 =  32,385
             sum                   =  64,770  >  32,767  // saturates, silently

Two details make this worse than it looks. The kernel multiplies the raw activation byte, before any zero-point correction — and the measured zero points in this model are 127 to 215, so the mean activation byte is 129 to 215. It is never small. And saturation clips rather than wraps, so the error is systematic: it always shrinks the largest partial sums, which are exactly the ones carrying the signal.

4.2 Why v0.2.0 and not v0.1.0: per-channel weight scales

The two revisions have the same architecture (BERT, 4 layers, hidden 312, 66 labels) and the same u8s8 scheme. The difference is the granularity of the weight scale.

v0.1.0v0.2.0 (shipped in 154)
Weight scale shape() scalar — per-tensor(312,) / (1200,) / (66,) — per-channel
Weights at exactly ±1270.00%0.33% in every matrix (= 1/312)
Weights with |w| ≥ 100~0%0.9% – 2.6%
Mean |w|, first attention matmul1.512.0
Mean |w|, layer-0 FFN intermediate2.624.9

With one scale for the whole matrix, only the single global maximum weight reaches ±127 and everything else is squashed small. With a scale per output column, every column maps its own maximum to ±127, so full-scale weights are spread uniformly through all 26 matrices and the typical magnitude rises roughly eight to ten times.

4.3 Why the collapse is total rather than noisy

The final classifier matmul alone, given exact upstream activations, shifts logits by at most 0.31 and flips nothing. A single-layer analysis would have cleared this model. It is the compounding through all 26 quantized matmuls that does the damage: each one sheds a little of its strongest activations, the representation drifts off distribution, and the classifier falls back to its prior. That prior is other, with address-level2 as the most frequent non-other class — which is exactly the observed output.

Root cause, stated once

Firefox 154 shipped tinybert-address-autofill v0.2.0 as an int8 u8s8 model with per-channel weight scales and no reduce_range. On x86-64 with AVX2 and without VNNI, ONNX Runtime accumulates adjacent products into int16 before widening, and per-channel scaling puts enough full-scale ±127 weights into every matrix that this accumulator saturates. The clipping error is systematic, compounds across 26 layers, and pushes the classifier off distribution so that it emits other or address-level2 for nearly every field.

5. The fix

Verified: re-export with reduce_range

reduce_range=True quantizes weights to 7 bits, bounding them to ±64 while keeping per-channel scaling. That caps a pair at 2 × 255 × 64 = 32,640, below the 32,767 limit, so saturation becomes impossible by construction rather than merely unlikely.

This was tested by rebuilding v0.2.0 with 7-bit weights — halving the int8 weights and doubling the per-channel scales — and re-running the same emulation:

Zero saturating pairs, and the emulated output is identical to the exact output rather than merely close. On this form the one-bit precision loss cost nothing measurable; confidence rose slightly (name 0.94 to 0.95, address-line1 0.61 to 0.70). That is six fields on one page, not an accuracy benchmark — the re-export still needs validating against the real evaluation set.

The test approximated reduce_range by halving already-quantized weights. A true re-export from the fp32 source will be at least as good, because it re-derives each scale from the original weights rather than inheriting a second rounding.

6. What is not yet proven

  • This is an emulation of the MLAS kernel, not a run on real AVX2 hardware. It models adjacent-k pairing with int16 saturation. The field-for-field agreement with the reporter is strong, but the decisive test is running v0.2.0 q8 on a pre-VNNI x86 machine.
  • The vendored runtime has not been inspected. Firefox's native ONNX runtime under dom/onnx is assumed to use the MLAS u8s8 AVX2 path. Very likely, not confirmed.
  • The wasm backend is unchecked. If ORT-web does not saturate the same way, users without native ONNX are unaffected, which narrows the affected population meaningfully.
  • Population sizing needs re-deriving against the real predicate: x86-64 without VNNI (pre-Ice-Lake Intel, pre-Zen-4 AMD) and nativeOnnxAvailable.
  • Firefox 155 needs the same check. The two-engine architecture that ships in 155 is a different code path and is not implicated here, but its formfill-encoder Remote Settings record carries no dtype and therefore also resolves to q8. Whether mozilla/form-autofill-embed has the same per-channel property should be measured the same way rather than assumed. Unlike v0.2.0, that model does ship an fp32 artifact, so pinning is a real option there.
