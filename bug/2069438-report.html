Rust login storage — is search performance a rollout blocker?

Bug 2069438 · Toolkit :: Password Manager · measured locally, 2026-09-16

No for autofill — measured at near parity with JSON. Yes for password import.

A real page-load autofill search is only 1.2–1.8× slower on Rust, because both backends pay the same dominant cost: origin matching runs in JS either way. CSV import is the regression — quadratic, and 1.7–5.7× slower than JSON across a 250 to 2,000 password import, with the gap widening as the file grows. The store-size distribution used to deprioritise this does not bound the import case.

Why the store-size distribution does not bound this

Comment 3 deprioritises the bug because only 0.2% of profiles hold 1,024+ logins. But import cost is driven by the size of the CSV, not the size of the existing store: the add phase re-reads a store that grows row by row, so a first-time import is quadratic on an empty profile. Someone migrating 3,000 passwords from another manager has zero saved logins at that moment. The percentiles describe existing profiles; the exposed population is "people who import a large file", and those are different sets.

Recommendation

  • Do not block the rollout. Steady-state search is unaffected at every realistic store size, and that is the overwhelming majority of what the feature does.
  • Fix the import path before anything that drives imports — onboarding, migration prompts, a switch-to-Firefox campaign. A 30 s unresponsive import sits in the migration funnel and self-selects for large password sets.
  • S3 is right; P3 looks too low. This is a regression against the backend being replaced, and the empty-profile exposure is not captured by the store-size percentiles.
  • Autofill is not where the work is. signon.schemeUpgrades and signon.includeOtherSubdomainsInLookup both default true, so page-load and autocomplete matching runs in JS and costs the same on either backend. Making that path faster is a separate, pre-existing problem.

Measured with an xpcshell harness driving LoginCSVImport.importFromCSV, Apple M4 Max. Import comparisons are a local opt build (no PGO/LTO), all three arms on the same binary; absolute times are faster on release builds, ratios hold. Per-search figures are harness timings of the shape page load sends (schemeUpgrades and acceptDifferentSubdomains both set): 200 timed searchLoginsAsync calls after 20 warm-up calls, one eTLD+1 per stored login so a search matches exactly one. The component breakdown alone comes from a Gecko profile on an artifact build, with the profiler's own 34% marker overhead excluded. Store-size percentiles are migration telemetry quoted from bug 2069438 comment 3 and were not independently verified. The 30 s figure for a 5,000-password import is extrapolated from the 2,000-row measurement; every other number is measured.
