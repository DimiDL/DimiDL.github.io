Important

1. A failed first load is never retried

Both tools
UrlClassifierRealTimeKeyService.sys.mjs:64–92 · correctness

#initPromise is set only once. If rs.get() throws, the error is logged, #config stays null, and the promise still resolves. Every later getKeyConfig() returns null without retrying. Recovery only comes from the next sync event: a push broadcast or the 24h poll (services.settings.poll_interval = 86400).

This is most likely on a fresh profile that is offline the first time a real-time check runs. With an empty local DB and no dump, get() has to go to the network.

Fix: register the sync listener only once, and clear #initPromise when get() fails so the next call retries. Add a test where get() rejects first and then succeeds.

#listening = false;
#synced = false;

async #init() {
  let rs = lazy.RemoteSettings(COLLECTION_NAME);
  if (!this.#listening) {
    this.#listening = true;
    rs.on("sync", ({ data: { current } }) => {
      this.#synced = true;
      // ...unchanged...
    });
  }

  let records;
  try {
    records = await rs.get();
  } catch (e) {
    console.warn(`Failed to load ${COLLECTION_NAME}`, e);
    this.#initPromise = null;
    return;
  }
  if (!this.#synced) {
    this.#config = parseKeyConfig(records);
  }
}
Question

2. The first call on a fresh profile waits on the network

Both tools
UrlClassifierRealTimeKeyService.sys.mjs:83–88 · performance

There is no safebrowsing-v5-rt-key dump in services/settings/dumps/main. When the local DB is empty, get() runs pullStartupBundle() and then a full sync() before it resolves. The first real-time lookup therefore waits on a network round trip.

Ask: is a dump planned? If not, does the caller fall back (for example, to local-list mode) when the key is slow to arrive or null? Either answer is fine, but it should be written down in the bug.

Question

3. A malformed record replaces a working key with null

Both tools
UrlClassifierRealTimeKeyService.sys.mjs:76–81 · correctness

If an invalid latest record is published, the service drops the last good key, sets null, and fires safebrowsing-realtime-key-changed. That is probably right, because a rotated key may already be invalid on the server. Please confirm it is intended and that consumers handle null after the notification.

Suggestion

4. Every caller gets the same mutable Uint8Array

Five-axis review
UrlClassifierRealTimeKeyService.sys.mjs:67 · correctness

getKeyConfig() returns the cached #config instance itself. If a JS consumer changes it in place (for example, zeroing it after use), the cached key is corrupted. The next isSameConfig check then compares against bad data. C++ callers are not affected, because XPConnect copies the array.

return this.#config?.slice() ?? null;
Suggestion

5. Test coverage gaps

Both tools
tests/unit/test_realtime_key_service.js · correctness
  • No test where get() fails or the DB is empty. This is the path in finding 1.
  • No test for a sync arriving while get() is still pending, which is the case the synced flag exists for. Make get() wait on a promise and emit sync in the meantime.
  • The tasks depend on each other's state through the singleton service. Add a short comment at the top of the file so anyone adding a task in the middle knows.
Suggestion

6. Explain why the synced flag exists

Five-axis review
UrlClassifierRealTimeKeyService.sys.mjs:72–90 · readability

A sync event that fires while get() is pending has newer records than get() will return, so it must win. That is not obvious from the code, and someone simplifying it later could bring the race back. Suggested comment:

// A "sync" event that fires while get() is pending carries newer records
// than get() will return.
Nit

7. Validation only checks the first byte

Module review
UrlClassifierRealTimeKeyService.sys.mjs:41 · correctness

The only structural check is config[0] == key_id, so a truncated config is accepted. This is fine if the OHTTP layer rejects it later. A cheap minimum-length check here would fail earlier and log a clearer warning.

Nit

8. Document the byte layout in makeKeyConfig

Five-axis review
tests/unit/test_realtime_key_service.js:18–31 · readability

Add a one-line comment giving the layout: key_id, KEM 0x0020 (X25519), 32-byte public key, cipher-suite length 4, KDF 1, AEAD 1. Readers can then check it against RFC 9458 §3.1.

Nit

9. The topic can fire before the first getKeyConfig() resolves

Module review
UrlClassifierRealTimeKeyService.sys.mjs:73–81 · FYI

If a sync arrives during init, observers are notified before the first caller gets its value. This is harmless, and the IDL comment already describes the contract correctly. No change needed.

What looks good

  • Security Input from Remote Settings is validated where it enters: key_id must be an integer from 0 to 255, base64 decoding is wrapped in try/catch (a non-string value throws a TypeError there, which is caught), and the first byte must match. Synced data is signature-verified by Remote Settings. Logs contain only public values.
  • Architecture Follows the pattern of the existing UrlClassifierRemoteSettingsService. The moz-src:/// path, MOZ_SRC_FILES, and components.conf entry match current tree conventions.
  • API The IDL documents the main-thread-only rule, the null case, and the observer contract. The change topic fires only when the key bytes actually change.
  • Race handling The synced guard correctly lets a newer sync win over a stale get() result. Remote Settings does not emit sync from get()'s sync-if-empty path (bug 1761953), so the guard only applies to real concurrent syncs.
  • Performance Initialization is lazy and the work is small: one record and a ~41-byte comparison.
  • Process Small, single-purpose change with tests, and a clear commit title and summary.
