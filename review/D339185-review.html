Important

1. While the key is missing, every call can trigger a Remote Settings sync from the server

Both tools
UrlClassifierRealTimeKeyService.sys.mjs:80–99 · performance / correctness

getKeyConfig() now reruns #load() whenever #config is null, and #load() calls RemoteSettings(...).get() with its defaults (syncIfEmpty: true). There is no dump for safebrowsing-v5-rt-key. With an empty local DB, get() runs pullStartupBundle() and then a full sync() (services/settings/RemoteSettingsClient.sys.mjs:474–516). If that sync fails (offline, captive portal, server error), the DB stays empty. Each later real-time lookup then starts another server round trip and waits for it. Concurrent calls are de-duplicated; calls in sequence are not.

The first lookup on a fresh profile also waits on the network (round-1 question 2, which has no answer yet).

Fix: read only local data and let the sync listener deliver the key. With an empty DB and syncIfEmpty: false, get() returns [] because emptyListFallback defaults to true. Precedent: AddonManager.sys.mjs:4784, ExperimentAPI.sys.mjs:677. If the first-use network fetch is wanted, keep it but rate-limit the retries.

records = await lazy.RemoteSettings(COLLECTION_NAME).get({
  syncIfEmpty: false,
});
Suggestion

2. A load in flight can bring back a key that a sync just removed

Module review
UrlClassifierRealTimeKeyService.sys.mjs:70–78, 98 · correctness

The round-1 synced flag is gone, replaced by this.#config ??= parseKeyConfig(records). That still lets a sync that sets a valid key win. But suppose a sync sets #config = null (record deleted or invalid) while get() is still resolving with the old records. #load then writes the old key back and sends no notification. This is rare, and the next sync corrects it.

#generation = 0;
// in the sync handler: this.#generation++;
async #load() {
  let generation = this.#generation;
  ...
  if (generation == this.#generation) {
    this.#config ??= parseKeyConfig(records);
  }
}

3. Every caller still gets the same mutable Uint8Array

Five-axis review
UrlClassifierRealTimeKeyService.sys.mjs:88 · correctness

Raised in round 1 and not yet changed. JS consumers in the parent process share the system global and get the cached instance itself. An in-place change corrupts the key for every consumer and confuses isSameConfig.

return this.#config?.slice() ?? null;
Suggestion

4. Limit the component to the parent process

Module review
components.conf:110–115 · architecture

Remote Settings is parent-only, but the IDL only says "Main thread only". Add 'processes': ProcessSelector.MAIN_PROCESS_ONLY so a content-process getService fails at once instead of creating an RS client (several toolkit components.conf files already do this, e.g. captivedetect).

5. Test gaps

Both tools
tests/unit/test_realtime_key_service.js:63–83 · correctness
  • test_retry_after_failed_load stubs get() to resolve [], so the catch path (rejection) is never run. Add stub.onFirstCall().rejects(new Error()), or test both.
  • No test that concurrent getKeyConfig() calls share one get().
  • No test for a sync while a load is in flight (finding 2).
  • The tasks depend on each other's state through the singleton. A note at the top of the file would help.
Nit

6. The IDL comment says notifications start after the first getKeyConfig()

Module review
nsIUrlClassifierRealTimeKeyService.idl:12–15 · readability

The sync listener is registered in the constructor, so notifications start once the service is instantiated (getService), even before getKeyConfig() is called. Either reword the comment or register the listener lazily.

Module review

Carried over from round 1. A truncated config passes. A minimum-length check (1 + 2 + Npk + 2 + 4) would fail earlier and log a clearer warning. It is also fine to leave the full check to the OHTTP layer, if the IDL says so.

Round-1 status

  • Fixed #1 Failed first load never retried: #loadPromise is now cleared in finally, and a test covers the retry. This is what introduces finding 1 above.
  • Resolved #3 A malformed record replaces the key with null: now stated in the commit summary as the intended behaviour, and tested (test_key_id_mismatch, test_invalid_base64, test_record_deleted).
  • Obsolete #6 Comment on the synced flag: the flag was removed (see finding 2).
  • Open #2 network wait on first call (merged into finding 1), #4 mutable array (finding 3), #5 tests (finding 5), #7 validation (finding 7), #8 byte layout comment (finding 8).

What looks good

  • Security The key comes from a signed Remote Settings collection. key_id is range-checked, base64 decoding is wrapped in try/catch, and the first byte must match. Logs contain only key_id, never key material.
  • Simplicity Shorter than round 1: a constructor-registered listener, a de-duplicated load promise, and ??= replace the init and synced bookkeeping.
  • Architecture moz-src:///, MOZ_SRC_FILES, private class fields, and an RS listener-plus-get() pattern that matches UrlClassifierRemoteSettingsService.
  • API The change topic fires only when the bytes actually change (test_unchanged_key_does_not_notify).
