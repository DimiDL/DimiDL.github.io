What the patch does. When a saved card is submitted with a new or changed security code, a new CreditCardSecurityCodeUpdateDoorhanger shows a "Save security code?" doorhanger with the security codes toggle. Turning the toggle off switches the doorhanger to the plain "Update payment method?" content in place, and updating then keeps the stored security code.

Verified correct

  • isNeeded() agrees with storage: the Rust store's getMatchRecords compares cc-csc, so a card whose only change is its security code reaches the prompt rather than being treated as a match.
  • The secondary action's callbackState getter is read when the button is clicked (#createActions closes over the params object), so "Save new payment method" really resolves create after the toggle is turned off.
  • cancel_update_doorhanger and disable_update_doorhanger already exist in metrics.yaml, so the new Dismiss and "Never save cards" actions record valid events.
  • Turning the toggle off goes through CreditCardSaveDoorhanger.recordToSave, which drops cc-csc while saving security codes is disabled, so the stored code is kept on update.
  • The new Fluent strings use hyphenated ids, flod's "Checkout" comment is applied, and the new ## section is closed by the existing bare ##.

Findings

Should fix The header and buttons go stale when the doorhanger reopens

CreditCardSecurityCodeUpdateDoorhanger.updateNotification

updateNotification() only writes the panel's attributes (label, buttonlabel, secondarybuttonlabel, dropmarkerhidden). PopupNotifications._refreshPanel resets those attributes every time the panel opens, using the notification's message and action labels. Those were formatted once in show(), while the toggle was still on. _showPanel also fires "showing" before _refreshPanel, which is why the patch has to wait for "shown".

How to hit it: turn the toggle off, click outside the doorhanger (persistWhileVisible keeps the anchor icon), then click the anchor or switch tabs and come back. The panel opens with "Save security code?", Save, Dismiss and the "Never save cards" dropmarker. Then "shown" fires and corrects them, so the stale labels flash briefly.

Suggested fix: in updateNotification(), update the notification itself (panel.notification: its message and the label/accessKey of mainAction and secondaryActions[0]), so _refreshPanel applies the current state on every open. Add a test that turns the toggle off, dismisses the panel, reopens it from the anchor and checks the labels.

Question Turning the toggle off when only the security code changed

test_security_code_toggle_off_saves_new_card

In this case the doorhanger switches to the plain update content, but neither button does anything useful:

  • "Update" changes nothing. recordToSave() drops cc-csc and every other field is unchanged, so it only bumps the card's last-used time.
  • "Save new payment method" saves an exact copy of the stored card without a security code. The test checks for this duplicate (creditCards.length == 2).

Is this what the UX spec wants? If not, the off state may need different content when nothing but the security code differs.

Question A security code submitted alongside other changes

CreditCardSecurityCodeUpdateDoorhanger.isNeeded

isNeeded() only looks at the security code. A submission that changes the name or expiry and brings a new code gets "Save security code?" with a Save button, and Save also updates those other fields. The card details line shows the new values, but the header never says the card is being updated.

Please confirm this is intended. The new tests only cover a change to the security code alone (withSecurityCodeUpdateDoorhanger fills every other field from TEST_CREDIT_CARD_1), so a test for the mixed case would help.

Nit The dismiss test can't catch an unexpected write

test_security_code_update_dismissed

The test reads storage straight after clicking Dismiss. That passes even if a write were still pending, so it can't catch a regression where Dismiss starts writing. Also, nothing covers "Never save cards" (disable) from this doorhanger.

Nit Duplicated CONTENT entry

CONTENT[CreditCardSecurityCodeUpdateDoorhanger.name]

The entry repeats anchor and options from the CreditCardUpdateDoorhanger entry. Spreading that entry would evaluate its getters once at definition time, so not spreading it is right, but the shared parts could become a constant.

Nit Comment on updateNotification

If the first finding is fixed, the comment can state the constraint directly, for example: "PopupNotifications only formats the header and buttons when the panel opens."

Nit Telemetry can't separate the two update flows

Clicks are recorded under telemetryObject = "update_doorhanger", the same as the plain update doorhanger, so the two flows can't be told apart. That's fine if nobody needs to tell them apart.
